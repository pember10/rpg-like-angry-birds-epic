# Development Plan: Loot Lab Prototype

## Objective

Build a small, single-screen Unity prototype that proves the central question:

> Does changing equipment create interesting gameplay and make players want to try one more build?

The prototype should prioritize loot, equipment effects, build experimentation, and fast replayability. Story, world map, quests, crafting, shops, and long-term progression should remain out of scope until the loot loop is validated.

---

# Phase 0: Prototype Foundations

## Goal

Create the technical base for a data-driven combat and loot prototype.

## Core Decisions

* Engine: Unity
* Language: C#
* Target-first mindset: mobile-friendly UI and input
* Architecture priority: combat logic independent from UI
* Data priority: equipment and effects should be easy to add, remove, and tune

## Deliverables

* Unity project structure
* Core folders for:
  * `Scripts/Combat`
  * `Scripts/Characters`
  * `Scripts/Equipment`
  * `Scripts/Loot`
  * `Scripts/UI`
  * `ScriptableObjects/Items`
  * `ScriptableObjects/Enemies`
  * `ScriptableObjects/Characters`
* Basic scene: `LootLabScene`
* Simple placeholder UI
* Basic debug tools for starting battles and granting items

## Success Criteria

* A battle scene can load.
* Placeholder characters and enemies can be spawned.
* Data assets can define characters, enemies, and items.

# Phase 1: Playable Combat

## Goal

Create the smallest possible turn-based combat loop.

## Features

### Player Party

Implement three player characters with simple stats:

* Health
* Attack
* Defense
* Speed or turn priority
* Equipment slots:
  * Weapon
  * Armor
  * Charm

### Enemy Team

Implement 4-6 simple enemy archetypes:

* Slime
* Mushroom
* Skeleton
* Bandit
* Turtle

Each enemy should have:

* Health
* Attack
* Defense
* Basic behavior

### Combat Loop

Implement:

* Start battle
* Determine turn order
* Select target
* Execute basic attack
* Apply damage
* End turn
* Check victory or defeat
* Award loot on victory

### Combat Log

Display simple readable messages:

* "Hero attacks Slime for 8 damage."
* "Slime is defeated."
* "You found Poison Dagger."

## Deliverables

* Functional turn-based battle
* Three-character party
* Enemy group
* Basic attack
* Victory condition
* Loot reward placeholder

## Success Criteria

* Player can start a battle.
* Player can attack enemies.
* Enemies can attack back.
* Player can win.
* Player receives a loot drop after victory.

# Phase 2: Data-Driven Equipment

## Goal

Make equipment the center of gameplay.

## Equipment Slots

Each character should support:

* Weapon
* Armor
* Charm

## Item Data

Each item should include:

* Name
* Rarity
* Description
* Slot type
* Visual/icon placeholder
* List of gameplay effects

Recommended Unity approach:

* `ItemData : ScriptableObject`
* `WeaponData`, `ArmorData`, and `CharmData`, or one generic `ItemData` with slot typing
* `EffectData : ScriptableObject` for reusable effects

## Initial Weapons

### Iron Sword

* Basic attack behavior

### Thunder Spear

* Attacks chain lightning to another enemy

### Poison Dagger

* Applies poison

### Boomerang Axe

* Hits multiple enemies

### Fire Wand

* Applies burn

## Initial Armor

### Knight Plate

* Reduces incoming damage

### Spiked Armor

* Reflects damage to attackers

### Storm Mail

* Grants shield when the wearer applies shock

### Druid Robe

* Heals wearer slightly each turn

## Initial Charms

### Lucky Coin

* Improves loot chance

### Blood Ruby

* Heals wearer on kill

### Fire Gem

* Increases burn duration

### Toxic Idol

* Increases poison damage

## Deliverables

* Equipment screen
* Inventory screen
* Equip/unequip flow
* Data-driven item definitions
* At least 5 weapons, 4 armor pieces, and 4 charms
* Equipment changes affect combat behavior

## Success Criteria

* Player can equip gear.
* Different gear changes combat outcomes.
* At least three distinct builds are possible:
  * Burn build
  * Poison build
  * Shock/shield build

# Phase 3: Status Effects and Interactions

## Goal

Make equipment combinations create memorable combat interactions.

## Status Effects

Implement:

* Burn
* Poison
* Shock
* Shield

## Baseline Behaviors

### Burn

* Deals damage over time.
* Can be extended by Fire Gem.

### Poison

* Deals damage over time.
* Damage can be increased by Toxic Idol.

### Shock

* Marks or damages enemies with lightning.
* Can trigger chain effects.
* Can activate Storm Mail.

### Shield

* Absorbs incoming damage.
* Can be generated by Storm Mail or future effects.

## Interaction Examples

### Thunder Spear + Storm Mail

* Applying shock grants shield.

### Fire Wand + Fire Gem

* Burn lasts longer, increasing total damage.

### Poison Dagger + Toxic Idol

* Poison becomes a stronger damage-over-time strategy.

### Blood Ruby + Boomerang Axe

* Multi-target attacks create more chances to heal on kill.

## Deliverables

* Status effect system
* Status effect UI indicators
* Combat log messages for status application and ticking
* Item-triggered status interactions

## Success Criteria

* Burn, poison, shock, and shield work reliably.
* Effects are visible in the UI.
* Players can intentionally combine items for stronger results.
* At least 4 clear item synergies exist.

# Phase 4: Loot Drops and Rarity Chase

## Goal

Make players excited by post-combat rewards.

## Rarity Tiers

Implement:

* Common
* Rare
* Epic
* Legendary

## Loot Rules

Keep the first version simple:

* Each battle grants one item.
* Rarity is rolled after victory.
* Lucky Coin modifies drop odds.
* Higher rarity can improve:
  * Effect strength
  * Effect duration
  * Trigger chance
  * Number of targets
  * Secondary bonus effect

## Example Rarity Scaling

### Fire Wand

* Common: Apply burn for 2 turns
* Rare: Apply burn for 3 turns
* Epic: Burn damages adjacent enemies
* Legendary: Burn spreads when an enemy dies

### Poison Dagger

* Common: Apply poison
* Rare: Stronger poison
* Epic: Poison can stack
* Legendary: Poison spreads on kill

### Thunder Spear

* Common: Chains to 1 enemy
* Rare: Higher chain damage
* Epic: Chains to 2 enemies
* Legendary: Shocked enemies grant shield when hit

## Deliverables

* Loot table system
* Rarity roll system
* Post-battle reward screen
* Inventory addition
* Item rarity display
* Simple rarity-based effect scaling

## Success Criteria

* Players receive random loot after battle.
* Rarity changes feel meaningful.
* Players can compare new loot against equipped gear.
* Players have a reason to replay battles.

# Phase 5: Loot Lab User Experience

## Goal

Turn the prototype into a focused testing sandbox.

## Main Screen Flow

The prototype should have a very simple loop:

1. View party
2. Equip gear
3. Start battle
4. Fight
5. Receive loot
6. Return to equipment screen
7. Try another build

## Required Screens

### Equipment Screen

Shows:

* Three characters
* Current weapon, armor, charm
* Character stats
* Equipped item descriptions

### Inventory Screen

Shows:

* Owned items
* Rarity
* Item slot
* Item effect description
* Compare/equip option

### Battle Screen

Shows:

* Player party
* Enemies
* Health
* Status effects
* Turn order
* Available actions

### Reward Screen

Shows:

* Dropped item
* Rarity
* Description
* "Equip Now"
* "Send to Inventory"
* "Next Battle"

## Deliverables

* Simple but usable UI flow
* Clear item descriptions
* Visible equipment changes
* Fast battle restart

## Success Criteria

* A tester can understand what an item does.
* A tester can quickly equip new loot.
* A tester can replay battles with minimal friction.
* The loop feels fast.

# Phase 6: Balance and Build Discovery

## Goal

Tune the prototype around build experimentation, not perfect balance.

## Build Archetypes to Support

### Burn Build

Core items:

* Fire Wand
* Fire Gem

Playstyle:

* Damage over time
* Longer fights
* Burn spreading or duration stacking

### Poison Build

Core items:

* Poison Dagger
* Toxic Idol

Playstyle:

* Scaling damage
* Strong against high-health enemies

### Shock Build

Core items:

* Thunder Spear
* Storm Mail

Playstyle:

* Chain damage
* Shield generation
* Multi-target pressure

### Sustain Build

Core items:

* Blood Ruby
* Druid Robe
* Spiked Armor

Playstyle:

* Healing
* Reflection
* Outlasting enemies

### Multi-Hit Build

Core items:

* Boomerang Axe
* Blood Ruby
* Lucky Coin

Playstyle:

* Hit many enemies
* Trigger more on-kill or loot-related effects

## Balance Goals

Avoid making one build obviously best. Instead, each build should feel strong in different situations.

## Enemy Design for Testing Builds

### Slime

* Low health
* Good for testing multi-hit and on-kill effects

### Mushroom

* Applies poison
* Tests sustain and shield builds

### Skeleton

* Basic attacker
* Good baseline enemy

### Bandit

* Higher damage
* Tests defensive builds

### Turtle

* High defense or shield
* Tests poison and burn builds

## Deliverables

* Tuned item values
* Tuned enemy stats
* At least 5 viable build combinations
* Combat log improvements for clarity

## Success Criteria

* Testers naturally try different gear.
* Testers notice item synergies without explanation.
* No single item trivializes all fights.
* Different enemies reward different builds.

# Phase 7: External Playtest

## Goal

Validate whether the loot loop is fun enough to continue the project.

## Playtest Format

Give testers a short session:

* 10-20 minutes
* No story explanation
* No tutorial beyond basic controls
* Start with basic equipment
* Let them earn loot naturally

## Observe

Track:

* Which items they equip
* Which items they ignore
* Which builds they discover
* Whether they read item descriptions
* Whether they replay voluntarily
* Whether they ask for more content
* Whether they say something like "I want to try one more build"

## Questions to Ask

After the session:

1. Which item was your favorite?
2. Did any combination feel clever or surprising?
3. Did you want to keep playing after getting new loot?
4. Was any item boring?
5. Was any item confusing?
6. Did you feel attached to any gear?
7. What build would you try next?

## Success Criteria

The prototype succeeds if testers:

* Replay battles voluntarily
* Experiment with gear without being told
* Remember items by effect
* Discover synergies
* Want more loot

The prototype fails if testers:

* Ignore loot
* Only equip the highest number
* Do not understand item effects
* Feel battles are repetitive
* Do not want to replay

# Risks and Mitigations

## Risk: Combat becomes the focus instead of loot

Mitigation:

* Keep combat simple.
* Make most interesting decisions happen through equipment.
* Avoid complex skill trees or tactical positioning early.

## Risk: Items feel like stat sticks

Mitigation:

* Require each item to have a visible gameplay effect.
* Use stats only as secondary tuning.
* Write item descriptions around behavior, not numbers.

## Risk: Too much content too early

Mitigation:

* Do not add story, world map, crafting, shops, or quests.
* Build only enough enemies to test item interactions.
* Add new content only when it supports loot testing.

## Risk: Synergies are hard to notice

Mitigation:

* Use clear combat log messages.
* Add visual status indicators.
* Use direct item wording:
  * "When you apply Shock, gain Shield."
  * "Poison deals more damage."
  * "Burn lasts longer."

## Risk: Replay loop is too slow

Mitigation:

* Fast battle restart.
* Quick equip flow.
* No unnecessary menus.
* Reward screen should immediately support "Equip Now" and "Next Battle."

# Decision Gates

## Gate 1: After Playable Combat

Question:

> Is the basic battle loop functional enough to test items?

If yes, continue to equipment effects.
If no, simplify combat.

## Gate 2: After Equipment Effects

Question:

> Do different items create noticeably different gameplay?

If yes, continue to status interactions.
If no, redesign item effects.

## Gate 3: After Status Interactions

Question:

> Are players discovering combinations?

If yes, continue to loot rarity.
If no, make synergies clearer and stronger.

## Gate 4: After Loot Chase

Question:

> Are players excited by drops?

If yes, prepare external playtest.
If no, improve rarity, item identity, and reward presentation.

## Gate 5: After External Playtest

Question:

> Do players want to try another build?

If yes, continue development.
If no, redesign the loot system before expanding.
